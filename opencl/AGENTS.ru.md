# AGENTS.md — opencl/

> Язык: [English](AGENTS.md) | **Русский**

## 1. Что здесь и что читать

`opencl/` — основная программа: C host в `src/`, OpenCL-ядра (`kernel.cl`, `ed25519_gpu.cl`),
`Makefile`, сгенерированный `embedded.h`, тесты и `third_party/`.

Перед изменениями прочитай:
- корневой `AGENTS.md`;
- `opencl/README.md`;
- `docs/architecture.md` — карта модулей, владение состоянием и дисциплина блокировок;
- `Makefile`;
- исходники и тесты, которых касается задача.

Не угадывай имена модулей и контракты: карта зависимостей описана в `docs/architecture.md`,
циклов между модулями быть не должно.

## 2. Локализация в этой папке

Основной язык — английский. Русские копии и переводы лежат рядом:

- `opencl/README.md` / `opencl/README.ru.md`;
- `opencl/AGENTS.md` / `opencl/AGENTS.ru.md`.

В комментариях к исходникам используй явные блоки `EN:` / `RU:` для содержательных комментариев;
не переводи тривиальные однострочные комментарии, идентификаторы, код OpenCL, флаги CLI,
JSON-ключи, magic-строки checkpoint и имена файлов.

Пользовательские строки `gramvanity` локализуются во время выполнения через `--lang en|ru` и
`GRAMVANITY_LANG` (по умолчанию английский). Добавляй оба языковых варианта вместе. Go-верификатор
`verify-go/w5addr` остаётся на английском.

Не переводи `third_party/`, сгенерированный `embedded.h` и бинарники.

## 3. Среда

Используй только MSYS2 UCRT64.

```bash
printf '%s\n' "${MSYSTEM:-}" "${OS:-}" "${MINGW_PREFIX:-}"
command -v gcc make
gcc -dumpmachine
```

Ожидается `UCRT64`, `Windows_NT`, `/ucrt64` и `x86_64-w64-mingw32`. Linux (gcc + OpenCL ICD)
поддерживается Makefile, но не подменяй им Windows-проверку. Если среда не соответствует
требованиям, остановись и сообщи об этом; не меняй компилятор или оболочку наугад.

## 4. Сборка

Полная Windows-сборка — из корня проекта:

```bash
bash ./build-windows.sh
```

Быстрая итерация в `opencl/`:

```bash
make            # gramvanity.exe
make clean
```

или из корня `make -C opencl`.

Особенности Makefile:
- все `src/*.c` компилируются одной командой; при добавлении или удалении `.c` обнови список
  `SRC` в `Makefile`;
- Windows: `LIBS = -lOpenCL -lbcrypt -static-libgcc`, Linux: `-lOpenCL -lpthread -lm`;
- объектных файлов нет, `make` пересобирает бинарник целиком;
- `embedded.h` должен существовать; если его нет — `make -C opencl embed`.

При ошибке `undefined reference to BCryptGenRandom` сначала проверь, что сборка идёт из UCRT64
и `OS=Windows_NT`. Только если ошибка сохраняется, используй документированный fallback:

```bash
make LIBS="-lOpenCL -lbcrypt -static-libgcc"
```

Не добавляй `-lbcrypt` постоянно и не правь Makefile ради обхода ошибки окружения.

## 5. embedded.h

`embedded.h` генерируется и уже лежит в репозитории; сборка не читает `.cl` напрямую.

```bash
make embed
```

Запускай после изменения:
- `kernel.cl`;
- `ed25519_gpu.cl`;
- `sha512_consts.h`;
- `english.txt`.

Нужен Python 3. `make embed` вызывает `python3`; если доступен только `python`, запусти
`python tools/embed.py` из `opencl/`. Скрипт проверяет SHA-256 словаря, поэтому не меняй
`english.txt` без понимания последствий. После генерации проверь diff `embedded.h` и включи его
в изменения. Не редактируй `embedded.h` вручную.

Исходники `.cl` — в UTF-8: их двуязычные комментарии `EN:`/`RU:` копируются в `embedded.h`
дословно, поэтому правка только комментария всё равно меняет сгенерированный файл, и её нужно
коммитить вместе с перегенерированным заголовком.

## 6. Проверки

Базовые, без GPU:

```bash
./gramvanity.exe --selftest-det
```

GPU- и интеграционные проверки:

```bash
./gramvanity.exe --list-devices
./gramvanity.exe --mode bip39-12 --bench 60
sh tests/test_det.sh
```

- `--selftest-det` — детерминированные unit-проверки, GPU не нужен.
- `test_det.sh` — 20 сценариев/113 проверок; нужен GPU и собранный бинарник. Запускать можно из
  `opencl/` или из корня: скрипт сам переходит в нужный каталог и использует временные папки.
- `GRAMVANITY_DEBUG=1` включает отладочный вывод подбора batch/chunk.
- Компиляция не доказывает корректность вычислений; при `SELF-TEST FAILED` не используй
  устройство для поиска.
- Если GPU нет, не выдавай `--selftest-det` за проверку GPU-пути: укажи, что GPU-набор не
  запускался.

После изменений в верификаторе (`verify-go/`) из корня проекта:

```bash
go vet ./verify-go
go test -count=1 ./verify-go
```

После изменений в документации:

```bash
python3 tools/check_i18n.py
```

## 7. Архитектура и контракты

- Модули и зависимости — в `docs/architecture.md`:
  `main -> {search, hits, checkpoint, selftest, gpu, detsearch, addresses, crypto, pattern,
  options, i18n, platform}`; циклы запрещены. `i18n` — листовой модуль (`tr()`, `--lang`,
  `GRAMVANITY_LANG`), поэтому его может подключать любой модуль.
- Общее состояние принадлежит одному модулю и экспортируется через его заголовок. Соблюдай
  дисциплину блокировок: `hit_lock`, `stat_lock`, `ckpt_lock`, `finish_lock`; не сужай
  критические секции без полного `tests/test_det.sh`.
- `search` запускает `../verify-go/w5addr[.exe]` и обменивается JSON-строками
  (`{"words","mode","net"}` → `{uq,eq,pub,...}`). Меняя формат, обнови обе стороны и Go-тесты.
- Checkpoint — бинарный формат v8; читает v2–v7. Любое изменение формата требует повышения
  версии, обратной совместимости и проверки round-trip/legacy в `--selftest-det`.
- Hit- и stop-файлы, а также имена целей — часть пользовательского контракта; не меняй их без
  необходимости. Понятный человеку текст пишется на языке запуска; ключи, теги и идентификаторы
  остаются английскими.
- Windows TDR: одно ядро не должно работать дольше ~2 секунд. PBKDF2 разбит на чанки (~0.25 с),
  подбор параметров — в `gpu.c`. Не делай длинных одиночных запусков.
- Startup self-test сравнивает GPU с CPU и блокирует поиск при расхождении; не обходи его.

## 8. Правила изменений

- Сохраняй совместимость C host и OpenCL-ядер; при изменении layout данных меняй обе стороны.
- Не удаляй и не отключай проверки/self-test ради прохождения теста.
- При изменении алгоритмов укажи, какие векторы и проверки подтверждают корректность.
- Не помещай секретные данные в исходники, тестовые фикстуры, логи и отчёты.
- Не меняй формат checkpoint и hit-файлов без необходимости и проверки совместимости.
- В итоговом сообщении перечисляй изменённые файлы, выполненные команды, результаты проверок и
  оставшиеся проблемы.
