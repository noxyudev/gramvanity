# Процесс выпуска версий

> Язык: **Русский** | [English](release-process.md)

Практическое руководство по выпуску новых версий gramvanity: версионирование,
коммиты, журнал изменений, чек-лист и работа автоматизации. Процесс управляется
тегом: вручную делаются только релизный коммит и один аннотированный тег —
сборку, упаковку и публикацию выполняет `.github/workflows/release.yml`.

## Версионирование

- Версии следуют [SemVer](https://semver.org/) — `MAJOR.MINOR.PATCH`:
  - **MAJOR** — несовместимые изменения: чекпоинты или hit-файлы перестают
    читаться старыми версиями, удаляется платформа или документированный
    флаг, меняется макет бинарников;
  - **MINOR** — новые видимые пользователю возможности: режимы, флаги,
    форматы вывода, поддержка кошельков;
  - **PATCH** — исправления ошибок, правки только документации, внутренний
    рефакторинг.
- Тег — аннотированный, с именем `vX.Y.Z` и сообщением `Release vX.Y.Z`.
- Версия тега должна совпадать с самой новой секцией версии в
  `CHANGELOG.md`/`CHANGELOG.ru.md`. У каждой опубликованной версии — свой
  тег: журнал изменений и список тегов всегда согласованы.
- Номер версии живёт только в журнале изменений и в теге. Архивы берут его
  из имени тега (`gramvanity-vX.Y.Z-<платформа>`, см. `release.yml`).
  Штампа версии в бинарниках пока нет — см.
  [Известные ограничения](#известные-ограничения).

## Коммиты

- Сообщения следуют
  [Conventional Commits](https://www.conventionalcommits.org/):
  `type(scope): краткое описание` в повелительном наклонении. Используемые
  типы: `feat`, `fix`, `docs`, `ci`, `build`, `test`, `refactor`, `chore`.
- Несовместимые изменения: `!` после типа/области и футер
  `BREAKING CHANGE:` (примеры в истории: `feat(verify-go)!`, `refactor!`).
- Видимое пользователю изменение в том же коммите добавляет свою строку под
  `[Unreleased]` в оба журнала изменений.

## Журнал изменений

`CHANGELOG.md` / `CHANGELOG.ru.md` следуют
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — по
SemVer. Два файла — языковая пара: менять оба в одном коммите (проверяет
`tools/check_i18n.py`, CI запускает его).

- `## [Unreleased]` постоянно присутствует в начале; изменения накапливаются
  там по мере коммитов.
- Секция версии: `## [X.Y.Z] - ГГГГ-ММ-ДД`.
- Категории внутри секции: **Добавлено**, **Изменено**, **Устарело**,
  **Удалено**, **Исправлено**, **Безопасность** (в английском файле: Added,
  Changed, Deprecated, Removed, Fixed, Security); пустые опускаются.
  Несовместимые строки помечаются `**BREAKING**` с описанием перехода.
- Записи пишутся для пользователей, а не для git: что изменилось, а не каким
  коммитом. Ссылки-сравнения для всех версий и для `[Unreleased]` — в конце
  файла.
- Обязательно попадают: видимое пользователю поведение, исправленные ошибки,
  удалённые возможности, изменения платформ и сборки, несовместимые
  изменения, новые настройки и переменные окружения, изменения форматов
  чекпоинтов и hit-файлов.
- По желанию: внутренний рефакторинг, обновления зависимостей, правки CI.
- Тело GitHub-релиза берётся из английского `CHANGELOG.md` (`release.yml`),
  поэтому записи должны читаться как release notes сами по себе.

## Чек-лист выпуска

### Подготовка

1. Вся запланированная работа закоммичена в `main`, CI зелёный
   (`.github/workflows/ci.yml` запускается на каждый пуш).
2. Языковые пары EN/RU обновлены вместе; `python3 tools/check_i18n.py`
   проходит.
3. Если менялись `opencl/kernel.cl`, `opencl/ed25519_gpu.cl`,
   `opencl/sha512_consts.h` или `opencl/english.txt`: `make -C opencl
   embed`, проверить diff `opencl/embedded.h` и включить его в изменение.
4. Локальная проверка (`AGENTS.ru.md` → «Проверка»):
   - `./opencl/gramvanity.exe --selftest-det` — после любого изменения
     C/OpenCL;
   - `go vet ./verify-go` и `go test -count=1 ./verify-go` — после
     изменения верификатора;
   - `bash ./build-windows.sh --check` — полный гейт сборки Windows;
   - если менялся GPU-путь: `./opencl/gramvanity.exe --list-devices`,
     короткий прогон `--mode bip39-12 --bench 60` и
     `sh opencl/tests/test_det.sh` (нужен GPU; только локально — CI
     выполнить его не может).
5. Оба журнала изменений несут изменения релиза под `[Unreleased]`.

### Выпуск

6. В обоих журналах: переименовать `[Unreleased]` → `[X.Y.Z] - ГГГГ-ММ-ДД`,
   оставить над ней новую пустую `[Unreleased]`, обновить ссылки-сравнения
   в конце файла.
7. Закоммитить оба файла:
   `chore(release): mark vX.Y.Z in the changelog`.
8. Поставить тег на релизный коммит:
   `git tag -a vX.Y.Z -m "Release vX.Y.Z"`.
9. Контроль: `git tag -l` показывает `vX.Y.Z`, версия совпадает с самой
   новой секцией журнала, `git status` чистый.
10. Отправить коммит и тег вместе: `git push origin main vX.Y.Z`.
11. Дождаться workflow `release` (Actions → release): две задачи сборки
    (linux-x64, windows-x64), затем `publish`. Занимает несколько минут.
12. Проверить страницу релиза: заголовок `vX.Y.Z`; тело из журнала
    изменений; четыре ассета — `gramvanity-vX.Y.Z-linux-x64.tar.gz`,
    `gramvanity-vX.Y.Z-windows-x64.zip` и `.sha256` к каждому.
13. Больше ничего не публикуется вручную: бинарники не коммитятся
    (`.gitignore`), `results/` не покидает машину.

## Что делает автоматизация

Пуш тега `v*` запускает `.github/workflows/release.yml`:

1. Собирает поиск на обеих платформах (Linux: `make -C opencl`; Windows:
   MSYS2 UCRT64 `make` — те же команды, что в CI).
2. Собирает верификатор: `go vet ./verify-go`, `go test ./verify-go`,
   `go build -trimpath -ldflags "-s -w"`.
3. Упаковывает архивы `gramvanity-<тег>-<платформа>` с сохранением макета
   репозитория — `opencl/gramvanity[.exe]`, `verify-go/w5addr[.exe]`,
   `docs/tg-wallet.md`, README, CHANGELOG, LICENSE, NOTICE — плюс
   `.sha256` к каждому архиву.
4. Публикует GitHub-релиз: тело = `CHANGELOG.md`, четыре файла из шага 3,
   плюс архивы исходников от GitHub и автоссылка на changelog.

Ручной запуск workflow (`workflow_dispatch`) только собирает и выгружает
архивы как артефакты workflow — релиз не создаётся. Используется для
проверки правок упаковки.

## Шаблон release notes

Секция журнала изменений и есть release notes; форма такая:

```markdown
## [X.Y.Z] - ГГГГ-ММ-ДД

<Одно-два предложения: суть релиза.>

### Добавлено
- ...

### Изменено
- ...

### Исправлено
- ...
```

Секции `Устарело`, `Удалено` и `Безопасность` добавляются, только когда для
них есть содержимое; остальные опускаются. Секция зеркалится в
`CHANGELOG.md`. Строка `**BREAKING**` называет затронутую команду, файл или
платформу и путь перехода.

## Известные ограничения

- Ни у одного бинарника нет `--version` и штампа версии при сборке; сборка
  опознаётся по имени архива или по changelog, с которым она поставляется.
- Тело релиза — весь `CHANGELOG.md`, а не только новая секция, поэтому
  release notes растут с каждым выпуском.
- `release.yml` повторяет `go vet`/`go test`, но не `--selftest-det`, а
  GPU-набор в CI не запускается никогда — их реально покрывают локальные
  шаги чек-листа.
